# Tool-Using LLM Agents: Architectures, Evaluation, Training, and Security — A Literature Survey

## TL;DR

- Tool use has become the defining capability of LLM agents: the field moved from prompt-level reasoning-acting loops such as ReAct and MRKL [1][2], through code-as-tool prompting [3][4] and self-supervised API learning in Toolformer [5], to fine-tuned, retrieval-grounded tool callers such as Gorilla [6] and large-scale data-synthesis pipelines like APIGen and ToolACE [7][8].
- Evaluation has stratified into three regimes — stateless single-turn API benchmarks (API-Bank, ToolAlpaca) [9][10], stateful multi-turn conversational benchmarks (τ-bench, τ²-bench, ToolSandbox, ToolTalk) [11][12][13][14], and long-horizon environment benchmarks (AgentBench, WebArena, GAIA, SWE-bench, MLE-bench) [15][16][17][18][19] — while a parallel "meta-evaluation" literature now argues many reported agentic scores are confounded by scaffolds, scorers and contamination [20][21][22].
- Training has shifted from supervised trajectory imitation to reinforcement learning with verifiable rewards over tool environments, jointly optimising the reasoner and the retriever [23][24][25][26]; context compaction for long-horizon tool loops has emerged as its own optimisation axis [27][28][29].
- Security is the binding constraint on deployment: indirect prompt injection through tool outputs and retrieved content remains highly effective against frontier models [30][31][32], with MCP servers as a newly characterised attack surface [33][34][35] and agent "skills" forming an unversioned supply chain [36][37].
- Reported defence gains are optimistic: adaptive attacks demonstrably bypass static-benchmark defences and monitoring-based control protocols [38][39], so robustness claims should be treated as upper bounds measured under non-adaptive adversaries.

## Background

An LLM agent, in the sense used throughout this survey, is a language model that is given a set of callable external tools (search engines, code interpreters, databases, REST APIs, or a whole computer) and is expected to decide *whether*, *which*, and *how* to call them across multiple turns to accomplish a task. MRKL articulated the earliest full architecture: a language model acting as a router between neural models and discrete expert modules such as knowledge sources, calculators and databases, motivated explicitly by extensibility and access to up-to-date information [2]. ReAct then supplied the execution pattern that most subsequent systems adopt — interleaving reasoning traces with task-specific actions, so the model plans, acts, observes the result, and re-plans, with reported gains in both accuracy and interpretability on decision-making and QA tasks [1].

Two early strands broadened what counts as a "tool". Program-aided and program-of-thought prompting made the tool a code interpreter: PAL prompts the model to emit executable Python so arithmetic and symbolic reasoning are delegated to a runtime [3], and Program of Thoughts explicitly disentangles computation from reasoning, reporting state-of-the-art math results and near-state-of-the-art financial results [4]. Toolformer instead demonstrated that the *training data* for tool use can be bootstrapped without human annotation, letting a model teach itself API calls in a self-supervised way and improving zero-shot performance across several tasks [5]. Together these three ideas — a reason-act loop, externalised computation, and self-generated tool-call supervision — define the problem the rest of the literature optimises.

A useful caveat sits at the foundation itself. One study argues that ReAct's apparent gains on sequential decision-making derive largely from similarity between prompt exemplars and queries rather than from genuine reasoning, cautioning that the field has not settled on *why* reasoning-acting loops help [40].

## Architectures and tool interfaces

**Routing, planner–executor separation, and tool making.** The lineage from MRKL's router design [2] runs through modular decompositions that split planning, tool invocation and result summarisation into separate components; one such Multi-LLM Agent finds that a modular decomposition outperforms a single-LLM approach, with the authors' framing that "small LLMs are weak tool learners" [41]. DEER adds a decision-aware layer that decides *when* to use a tool versus answering directly, targeting generalisability of the decision itself [42]. A second architectural family splits the tool *proposer* from the tool *user*: LATM has an LLM create its own tools and then use them, improving efficiency and cost-effectiveness [43], and CREATOR similarly disentangles "abstract" planning reasoning from "concrete" tool execution via tool creation [44]. A third family is retriever-then-executor: Gorilla is a fine-tuned LLaMA that writes API calls more accurately and flexibly than GPT-4 and pairs the model with a document retriever to adapt to documentation changes and mitigate hallucination [6]. Chains of tools generalise this beyond hand-designed pipelines, letting an LLM discover tool usages programmatically [45].

**Tool retrieval and representation.** Once tool sets exceed the context window, tool selection becomes a retrieval problem. ToolDreamer generates synthetic tool descriptions to align queries with tools when the tool set is too large to fit in context [46], and preference-optimised retrievers have been trained specifically for tool selection [47]. Tool *documentation quality* turns out to matter as much as retrieval machinery: converting verbose documentation into concise structured "tool instructions" improves tool use [48], simple documentation expansion measurably boosts tool retrieval [49], and one diagnostic finds a dissociation between retrieving a tool and genuinely understanding it on ambiguous queries [50]. This concern recurs at the protocol level, where poorly written MCP tool descriptions are found to degrade agent performance and efficiency [51] and tool-selection accuracy is reported to degrade beyond certain tool-count thresholds [52].

**Constraining the interface.** Because malformed calls are a leading failure mode, some work moves correctness into decoding: a finite-state-machine-guided decoding algorithm reduces syntax errors and improves tool selection without fine-tuning or documentation changes [53], and at least one prompt-engineering-only method claims stable tool calling without any fine-tuning [54]. On-device settings add a deployment constraint, addressed by decoupled fine-tuning of the agentic components [55].

**Data generation for tool calling.** Modern tool-calling ability is largely bootstrapped. APIGen is an automated pipeline producing verifiable, diverse function-calling datasets with strong reported results on the Berkeley Function-Calling Benchmark [7], ToolACE uses self-evolution synthesis to generate accurate and diverse tool-learning data that improves function calling in smaller models [8], and ToolForge synthesises multi-hop search data without real-world APIs [56]. API-BLEND supplies large corpora for training and benchmarking API LLMs [57], and UniToolCall standardises toolset construction, training-data generation and evaluation [58]. Two distinct strategies therefore coexist — self-supervised/self-evolution synthesis [5][8][56] versus curated corpora [57] — with limited head-to-head comparison in the retrieved literature.

## Benchmarks, evaluation, and measured reliability

**Three evaluation regimes.** The benchmark landscape stratifies by statefulness. The first regime is single-turn API use: API-Bank provides 73 executable API tools and 314 annotated tool-use dialogues [9], ToolAlpaca uses 3,000 simulated cases and shows compact models can reach generalised tool use comparable to larger models [10], MetaTool tests *whether and which* tool to use [59], and AppBench tests multi-API planning across apps [60]. The second regime is stateful, multi-turn, conversational evaluation: ToolSandbox was explicitly motivated by the observation that prior work evaluated "either over stateless web services (RESTful API), based on a single turn user prompt, or an off-policy dialog trajectory" [13]; ToolTalk evaluates tool usage in conversation [14]; τ-bench tests an agent against a simulated user with domain-policy adherence [11]; and τ²-bench extends this to a "dual-control environment" [12]. ToolLLM/ToolBench anchors the massive-API end of this space with 16,000+ real-world REST APIs, DFSDT decision-tree annotation and the ToolEval auto-evaluator [61]. The third regime is long-horizon environments: AgentBench [15], WebArena's reproducible websites [16], Mind2Web's real websites with crowdsourced actions [62], GAIA's real-world reasoning and tool-use questions that show a significant human–AI gap [17], SWE-bench's real GitHub issues, on which models "can only handle the simplest tasks" [18], and MLE-bench's 75 Kaggle competitions, where the best setup reached bronze-medal level on some competitions [19].

**Scope and verification caveats.** Two limitations apply to this section and, where relevant, to the survey as a whole. First, source diversity: retrieval was constrained by rate limits on the arXiv and general web search backends during this session, so the corpus is dominated by Hugging Face-indexed paper records; the `web` source family (vendor documentation, leaderboard pages, standards guidance) is therefore not represented, and several canonical systems discussed here are cited through their Hugging Face paper records rather than publisher or vendor pages. Second, a sample of the quantitative claims below could not be independently re-verified, and a number of cited records carry 2026 publication dates that were not independently confirmed against publisher metadata; these figures should be treated as reported-by-the-source rather than audited.

**Meta-evaluation and confounds.** A substantial critical literature now questions what these numbers measure. Best-practice work for rigorous agentic benchmarks documents overestimation risks [20], a validity audit of tool-calling evaluation finds evaluator misalignment and variance [21], and a "science of AI agent reliability" framing questions rank stability and predictive validity [22]. Error-mode characterisation has itself become a first-class object: SpecTool characterises error patterns in tool-use LLMs [63] and TRAJECT-Bench scores trajectories along tool selection, parameterisation and ordering [64]. Reproducibility motivated StableToolBench's virtual API server with caching [65] and SEAL's GPT-4 API simulator testbed [66], both of which exist because live-API evaluation is unstable and therefore hard to compare across papers. On the reliability of testing itself, high-fidelity simulation of user traits such as impatience changes agent behaviour, indicating that simulated-user design is a measurement variable rather than a neutral harness [67].

## Training, planning, and optimisation

**From imitation to reinforcement learning with verifiable rewards.** The current training frontier is RL over tool environments. Agent-R1 generalises the MDP for end-to-end RL with tool environments, extending RL methodology beyond single-turn RLHF [23]; notably, RLTR shows that tool-use *process completeness* can serve as a reward signal even without gold answers, improving action planning [24]. For agentic search specifically, the reward signal can be decomposed: CoSearch jointly trains the reasoning agent and a generative document ranker with GRPO and reports that jointly trained reasoning and ranking beats fixed-retrieval systems [25], while Agentic-R learns a retriever using both local relevance and global answer-correctness signals, alternating between search-agent and retriever training [26]. An empirical study isolates the key design factors for reasoning–search interleaved RL agents as reward formulation, base-LLM characteristics, and search-engine integration [68], and the area has attracted survey-level consolidation [69].

**Reflection is useful but double-edged.** Reflexion's original formulation applies verbal reinforcement — linguistic self-reflection with episodic memory and no weight updates [70]. Subsequent work folds reflection into training: WebSeer trains a deeper search agent with RL combined with self-reflection [71], Agent-R uses iterative self-training with Monte Carlo Tree Search so the model learns to recover from errors in real time [72], and Re-ReST combines reflection with *external* feedback as a self-training signal [73]. Pivotal-aware self-feedback retries localise the retry to pivotal errors to cut interaction cost while preserving learning signal [74]. The counter-evidence is important: a dedicated study finds reflective agents can store confident but incorrect self-reflections ("memory confabulation"), causing persistent errors even after environment resets, and introduces a Reflection Repetition Rate metric to measure it [75]. Curriculum and exploration control further modulate agentic RL, via self-imitation with progressive exploration and trajectory-level entropy control [76] and retrospective dual intrinsic feedback [77].

**Context management as an optimisation axis.** Long-horizon, many-tool-call agents spend most of their budget on context, and this is now treated as something to optimise rather than merely truncate. CompactionRL jointly optimises task execution *and* summary generation via RL with context compaction, improving long-horizon coding performance [27]; Continuous Context Management compacts at every turn and has been evaluated on TerminalBench-2 [28]. Self-GC treats agent context as indexed, recoverable objects with controlled lifecycles rather than heuristic text cleanup [29], and a related design models context as a "session environment" backed by an append-only event log and a persistent Python kernel [78]. Elastic context orchestration [79], Git-like context control [80] and typed memory blocks with runtime "proprioceptive" dashboards [81] form a recognisable design family. A dated report that current compactors can retain only a small fraction of injected session constraints flags the correctness risk this family is racing against [82].

**Multi-agent orchestration and retrieval-as-a-tool.** Multi-agent systems are now trained at the coordination level rather than only per agent: one study attributes multi-agent RL instability to global normalisation mismatch and fixes it with agent-specific advantage normalisation [83], while another frames RL for LLM multi-agent systems as learning "orchestration traces" — spawning, delegation, communication, aggregation and stopping — with reward design and credit assignment as the core axes [84]. Systems work externalises search progress into shared structured state to prevent repetitive loops [85] and decouples search into specialised roles [86], while cost-aware routing attacks the cost–performance barrier in graph-based multi-agent systems [87]. End-to-end agents with scalable toolsets combine memory folding with RL and autonomous tool *discovery* [88], and multi-turn RL with LLM-simulated users trains agents on dynamic interactive tool use [89]. In parallel, the RAG-versus-tool debate has converged on agentic retrieval: a benchmark study finds agentic search can enhance dense-RAG performance and reduce reliance on explicit graph structures, though GraphRAG still wins on complex multi-hop reasoning [90]; interleaved designs let models actively manipulate the corpus [91] or scale via hierarchical retrieval interfaces [92], and token-efficient variants target the cost side by compressing retrieved content and reducing reasoning steps [93]. Surveys frame this as a general convergence of retrieval and reasoning systems [94], with benchmarks for the intermediate sub-capabilities of such pipelines [95]. Runtime repair complements training, diagnosing failures from execution traces and applying graph-guided interventions without modifying the agent [96], and harness-aware training adapts compact models to evolving agent-harness configurations [97].

## Safety, security, and deployment

**The core threat is indirect prompt injection.** AgentDojo provides a dynamic environment with security test cases and utility tasks to evaluate attacks and defences for agents that consume untrusted data through tools, and is a widely used baseline for measuring the attack-success-versus-utility trade-off [30]. InjecAgent benchmarks indirect prompt injection in tool-integrated agents with 1,000+ test cases, showing meaningful attack success across deployed tool-use patterns [31]. Attack success remains high in realistic conditions: web agents stay vulnerable to simple injections [32], and harmful instructions delivered through "skill" files that coding agents execute with user permissions have been measured at up to roughly 80% vulnerability for frontier models [98], with such skills-based injections described as "realistic and trivially simple" [99]. Exfiltration is concrete rather than hypothetical: simple prompt injections on banking tasks leak personal data the agent observed during execution, though safety alignment often protects the most sensitive fields such as passwords [100].

**MCP and skills as new attack surfaces.** With the Model Context Protocol becoming the dominant tool-integration layer, tool poisoning, tool squatting and rug-pull attacks have become a distinct research class. MCPTox benchmarks tool-poisoning attacks against real-world MCP servers and finds widespread susceptibility with "current safety measures" ineffective [35]; ETDI targets tool squatting and rug pulls by adding OAuth-enhanced, versioned tool definitions with policy-based access control [34]; and a large-scale empirical study of MCP servers identifies distinct vulnerabilities and code smells requiring MCP-specific security measures [33]. Beyond servers, a copy-network study of shared SKILL.md instructions and scripts shows that agent skills form a software supply chain *without a registry, versions, or provenance*, leaving the origin of copied skills and the reach of a fix unknown [36], while a large-scale empirical study finds widespread prompt-injection, data-exfiltration and privilege-escalation risks across skills [37]. A systematic analysis of agentic coding assistants finds vulnerabilities spanning skills, tools and protocol ecosystems, with defences of limited effectiveness against adaptive attackers [101].

**Defences and why reported gains are optimistic.** Defence work splits into three families. Detection-on-re-execution offers provable guarantees by masking the suspected injected instruction and re-running the trajectory, flagging action-sequence deviation from user-task-only behaviour [102], complemented by reusable design patterns that trade utility for injection resistance [103]. Capability and privilege control is the second family: programmable fine-grained tool-call privilege policies preserve utility while restricting authority [104], offline reconstruction of least-privilege tool access enforced online [105], access-control policies learned from execution traces to gate calls on input context and control-flow dependence [106], and authority checks with deterministic gates at the execution boundary [107]. The third family converts governance into runtime checks: verifiable safety-policy compliance via logical reasoning and probabilistic rule circuits [108], unstructured governance documents compiled into auditable runtime guardrails [109], and symbolic guardrails argued to give stronger guarantees than learned filters in high-stakes domains [110]. Multi-stage defence-in-depth has been proposed specifically for MCP [111], and environment-layer sandboxing that restricts "ambient authority" at the HTTP layer reduces attack impact at acceptable performance cost [112], with comparable multi-layered protection proposed for AI browser agents [113]. Red-teaming frameworks generate black-box injections automatically [114].

The critical caveat is that these gains are usually measured against static adversaries. Adaptive, optimised attacks expose static-benchmark defences as superficial [38], and "agent-as-a-proxy" attacks turn the agent into a delivery vehicle that bypasses even large-scale monitoring-based AI control protocols [39]. Combined with the MCPTox finding that current safety measures are ineffective against tool poisoning [35] alongside claims of high-accuracy MCP defence-in-depth [111], the honest reading is that reported defence success rates are upper bounds under non-adaptive evaluation.

**Deployment and its limits.** Computer-use and coding agents are shipping: Claude 3.5 Computer Use was the first frontier model offering public-beta computer use as a GUI agent [115], SWE-agent introduced the agent-computer-interface concept to reach state-of-the-art software-engineering task resolution [116], and an analysis of Claude Code traces five human values to thirteen design principles and implementation choices, including its core while-loop plus safety, context-management and extensibility systems [117]. On the enterprise side, SOP-Bench supplies 2,000+ expert-authored standard-operating-procedure tasks across 12 business domains for evaluating multi-step tool orchestration in industrial automation [118], but current agents detect *alerted* issues while failing at silent intrusion discovery and verified remediation planning [119], and trace-auditable vulnerability mapping across planning, memory, retrieval, tool use and delegation finds comparable weaknesses in deep-research agents [120]. Human-like query datasets for MCP tool retrieval were missing until recently [121], and general uncertainty work motivated by models stating incorrect conclusions in fluent, authoritative tones speaks directly to when an agent should defer or request approval [122]. Cost and latency of multi-step loops remain comparatively under-evidenced: only a minority of retrieved systems work targets token or cost reduction explicitly [93][87], and most sources report task accuracy rather than wall-clock latency or monetary cost.

## Trends and open problems

**Trend 1 — RL with verifiable rewards has displaced SFT as the frontier recipe.** Within the last two years the dominant training story moved from trajectory imitation to RL over tool environments [23][24], extended to joint optimisation of reasoning and retrieval [25][26], with reward formulation identified as a primary design variable [68] and consolidation into survey form [69]. The unresolved problem is credit assignment across long tool trajectories: outcome-only rewards give no per-step signal, and the field's responses — process-quality rewards [24], pivotal-error targeting [74], intrinsic feedback [77] — are early-stage and not yet compared under common protocols.

**Trend 2 — context is being engineered, not merely filled.** Context compaction and memory management have become explicit optimisation targets for long-horizon tool loops [27][28][29][78][79][80][81]. There is no agreed metric for compaction fidelity, however, and evidence that compactors can drop most injected session constraints indicates that efficiency and correctness are in tension rather than aligned [82].

**Trend 3 — evaluation is consolidating toward stateful, tool-and-user-in-the-loop settings.** Static single-turn API benchmarks are increasingly treated as insufficient; the frontier has moved to stateful conversational benchmarks [13][14][11][12] and long-horizon environments [15][16][17][18][19], while simulated-user behaviour is itself recognised as a measurement variable [67]. Benchmarks for intermediate capabilities [95], trajectory-aware scoring [64] and error-mode taxonomies [63] all point to a shift from aggregate scores to diagnostic evaluation.

**Trend 4 — reproducibility and validity are now first-class research objects.** Virtual API servers and simulators exist because live-API evaluation is unstable [65][66]; audits of evaluator alignment and benchmark validity find systematic overestimation risks, rank instability and variance [20][21][22]. The open problem is institutional rather than technical: there is still no standard for reporting scaffold, scorer and version alongside agent scores.

**Trend 5 — security has moved from model alignment to system and supply-chain integrity.** The threat model has broadened from single injections [30][31] to protocol-level poisoning [33][34][35], skill supply chains lacking provenance or versioning [101][37][36], and adaptive attackers that defeat static defences [38][39]. The most consequential open debate is whether detection-style defences can ever be robust or whether the field must move to capability-restriction designs with provable guarantees [102][104][105][106][107], and how such guarantees compose across multi-agent hierarchies where authority propagates across boundaries.

**Trend 6 — real-world deployment is outrunning reliability evidence.** Coding and computer-use agents are in production [115][117][116] and enterprise evaluation suites now exist [118], yet agents still fail at open-ended, self-directed subtasks [119][120], and cost/latency evidence remains thin relative to accuracy evidence [93][87]. Relatedly, tool *documentation* quality is an under-appreciated lever on real deployments [49][48][51][52], and human-like evaluation data for large tool registries has only recently begun to appear [121]. Closely related, reflective agents can persist confident but incorrect self-generated memory [75], which argues for grounding reflection in external signals rather than treating it as free supervision [73][70].
